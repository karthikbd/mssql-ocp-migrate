# Dependencies and scanning policy

## How dependencies are chosen, obtained and tracked

- **Runtime:** none. `pyproject.toml` declares `dependencies = []` and a test fails the build if the wheel
  declares any. The SQL Server driver (python-tds) is **vendored** under `src/mssql_ocp_migrate/_vendor/` at a
  pinned version, listed in `ci/vendored.txt` and in the release SBOM, with its license in
  `THIRD_PARTY_NOTICES.md`. Optional drivers (pyodbc, pymssql) are used only if the user already
  installed them.
- **Choosing a new one** (vendored code or CI tool): it must be actively maintained, under a license
  compatible with MIT, free of known vulnerabilities, and worth its weight; a new runtime dependency is
  normally refused. The decision is recorded in the pull request that adds it.
- **Obtaining:** CI tools are installed from PyPI with `pip install --require-hashes` from the locked
  files `ci/requirements-*.txt` (generated by `uv pip compile --universal --generate-hashes` from the
  `.in` files). GitHub Actions are pinned to full commit SHAs. The fuzzing image is pinned by digest.
- **Tracking:** Dependabot proposes updates weekly for Actions, the CI locks and the fuzzing image; each
  update goes through the same pull-request checks as any change.

## Software composition analysis (SCA)

- `vulnerability-audit.yml` runs `pip-audit` against the vendored driver and every locked CI tool, on
  every change to them and weekly. On pull requests, GitHub's dependency review blocks any change that
  adds a dependency with a known vulnerability of **moderate** severity or higher.
- **Threshold:** a known vulnerability of medium or higher severity that affects mssql-ocp-migrate must be fixed
  before the next release, and within 60 days at the latest (30 days for high or critical). Low-severity
  findings are fixed in the next regular update. A finding that does not affect mssql-ocp-migrate is recorded
  in `vex.openvex.json` with the reason.
- **No release with open violations:** the release checklist ({doc}`releasing`) requires a clean audit.

## Static analysis (SAST)

- CodeQL (security queries) runs on every push and pull request and weekly; `ruff` (including the
  Bandit-derived `S` rules) and `mypy --strict` run on every push and pull request.
- **Threshold:** every CodeQL alert of **medium** severity or higher must be fixed or dismissed with a
  written reason before merging; `ruff` and `mypy` must be clean (a justified `noqa` is allowed and
  reviewed). These checks are required to pass before a pull request can be merged into `main`.
